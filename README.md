# MADAR — مَدار

**THE CITY IN MOTION.**

MADAR is a smart-city digital twin. You explore a simulated city, change how it runs — signal timings, road closures, incidents, demand — run the morning again, and compare what happened. Underneath the cinematic front end is a working system: a deterministic traffic simulation engine, a NestJS API over PostgreSQL + PostGIS, a BullMQ job queue with a simulation worker, and real-time progress over WebSockets.

> **Synthetic data.** Madar is a fictional reference city generated by the engine. No real-world statistics are used or implied, and every image on the site was rendered from the synthetic city by MADAR's own offline renderer.

## Live demo (GitHub Pages)

Pushing to `main` publishes a static build with GitHub Pages (enable once: **Settings → Pages → Source: GitHub Actions**), at `https://<user>.github.io/<repo>/`.

- The **landing page** is identical to the full build.
- Every app entry point (*Sign in*, *Enter MADAR*, *Explore MADAR*, *Open the Scenario Lab*, *Create an account*) first shows a **demo notice**: synthetic data, no registration, no accounts.
- The **application runs in demo mode**. The same pages call the same API routes, answered in the browser by `apps/web/src/demo/backend.ts`:
  - runs execute the real `TrafficSimulation` in a Web Worker;
  - input is validated with the shared Zod schemas and the engine's own validator;
  - comparisons, Webster proposals, energy and reports use the same engine and shared functions as the server.
- On a first visit the sample study (baseline, Webster re-timing, Orbit Boulevard closure) is **computed in the browser in a few seconds**. Its numbers match the landing page exactly (same engine, same seed; covered by a unit test).
- The visitor's scenarios, runs and reports are kept in **localStorage + IndexedDB** (memory only when storage is blocked). *Reset demo* clears them.

Build and test it locally:

```bash
NEXT_PUBLIC_BASE_PATH=/madar pnpm --filter @madar/web build:static   # → apps/web/out
# serve apps/web/out so that it is reachable at http://localhost:8090/madar/, then:
pnpm exec playwright test -c tests/e2e/demo.config.ts
```

Force demo mode in local development with `NEXT_PUBLIC_DEMO=1 pnpm --filter @madar/web dev`.

## Quick start (macOS)

Requirements: **Node 22**, **pnpm 10** (`corepack enable`), **Docker Desktop**.

```bash
git clone <your-fork> madar && cd madar
cp .env.example .env
# put a real secret in JWT_ACCESS_SECRET:  openssl rand -base64 48

pnpm install
docker compose -f infrastructure/docker-compose.yml up -d db redis

pnpm build:packages          # engine, db, shared
pnpm db:migrate              # creates PostGIS + all tables
pnpm db:seed                 # city, roles, demo accounts, sample project (uses DEMO_PASSWORD)

pnpm dev                     # API :4000, worker, web :3000
```

Open <http://localhost:3000>. Demo accounts (password = `DEMO_PASSWORD` from your `.env`):

| Email | Role |
|---|---|
| `planner@madar.dev` | planner — owns the “Morning Peak Study” project |
| `viewer@madar.dev` | viewer — read-only member of that project |
| `admin@madar.dev` | admin — user management and audit log |

API docs (OpenAPI/Swagger): <http://localhost:4000/api/docs>.

Without Docker: install Postgres 16 with PostGIS 3 and Redis 7 (`brew install postgresql@16 postgis redis`), create a `madar` role that can `CREATE EXTENSION`, and point `DATABASE_URL` / `REDIS_URL` at them.

## The demo in five minutes

1. **Landing page** — scroll the descent over the bay; switch layers on the system map; watch the engine run live in your browser; scroll the closure story.
2. **Sign in** as the planner → **Scenario Lab** → open the baseline → *Run simulation* (watch live at 60×, or “as fast as possible”).
3. Create a variant → **Propose with Webster** → *Apply all* → *Save and run*.
4. **Compare latest run with baseline** — average travel time drops by roughly 17 % for seed 42.
5. **Save as report** → open the printable version.
6. **City Explorer** — orbit the 3D city, click a road to see its results or close it in a scenario; scrub the playback of every simulated vehicle.

## Testing

```bash
pnpm test                    # unit + integration (needs Postgres/Redis; see below)
pnpm --filter @madar/sim-engine test
pnpm --filter @madar/db test        # uses TEST_DATABASE_URL (default postgres://madar:madar@localhost:5432/madar_test)
pnpm --filter @madar/api test       # spins up the full Nest app on a random port, Redis db 5

# end to end (with `pnpm dev` running and the database seeded)
DEMO_PASSWORD=... pnpm test:e2e

# visual QA screenshots at 360 → 1920 px
node tests/visual/shoot.mjs ./qa
```

Create the test database once: `createdb -O madar madar_test` (PostGIS is created by the migration).

## Known limitations

- The traffic model is **mesoscopic** — no lane changing, no turning conflicts inside a junction, one vehicle class, no pedestrians or transit. It is built for comparing scenarios under the same assumptions, not for calibrated prediction.
- Energy and emissions are **model estimates** from stated, illustrative coefficients; they are labelled as such everywhere.
- One city (Madar) ships; the schema supports more.
- Pausing holds the worker's job slot; with `WORKER_CONCURRENCY=2` two paused runs block new work until resumed or cancelled.
- The landing imagery is a real-time-engine render (Three.js), not a path-traced film render. The pipeline accepts licensed photography as a drop-in replacement for any still (`apps/web/public/media`).
- The GitHub Pages demo has no server. Accounts, roles, project sharing and the PostGIS spatial queries exist only in the full stack. Demo data lives in one browser, a run stops if its tab is closed, and playback frames are kept for the 8 most recent runs.
- Socket.IO runs on a single API instance; scaling out needs the Redis adapter (`@socket.io/redis-adapter`) — the pub/sub wiring already goes through Redis.

## Future improvements
